# 迷雾之都（MistCity）— 设计

本文各项决定均经用户确认。改判的理由与基准表原文并列记下，方便日后翻旧账。

## 核心幻想

不做给谁看的故事。做一张桌子，桌上摊满牌，反复试怎么把它们叠在一起。

## 体验支柱

| 支柱 | 指的是 |
|---|---|
| 发现 | 合出一张事先不知道存在的牌，那一下是奖励 |
| 取舍 | 每张牌的产出间隔不同，长的稳、短的急，牌位有限 |
| 还债 | 进食每 60 步结算一次，欠着会死人；房屋能补人，补的人立刻自己吃一份 |

## 核心循环

一个动作：**把一张牌叠到另一张上**。
叠在一起之后产出什么，由承载者（底下那张）的牌种决定。

| 底下那张 | 输入 | 结果 | 做错的后果 |
|---|---|---|---|
| 与那一摞有配方 | 那一摞里配方要的那几张：底下那张、压在它上面的每一张、再加上刚拖过来的那张 | 消耗的那几张消失，合成出一张新牌；摞上多出来的那几张留在桌面上 | 材料没了，人还在 |
| 产粮牌 | 一张牌叠上去 | 两张都在，上面那张按间隔产出 | 只空转，不损失 |
| 房屋牌 | 一张牌叠上去 | 上面那位住进去，占一个空位 | 占着不产，等满 2 人才生人 |

判定次序：先问配方，再问能不能接上去。两条都不通才什么都不发生。

**整摞算进配方输入**：拖放手势只有两端（拖一张、压一张），
而房屋那三条配方全是三份输入，按「两张」判的话玩家合不出房屋牌。
**住户与其他牌一样参与配方匹配**：不然「屋 = 棚 + 2 石」永远凑不齐 ——
压在房屋上的石已经先成了住户。
副产品：柴住进棚之后，再压一张柴上去，两张柴当场合成掉，房屋就住不满。
这是这一条规则本身的结果，不是缺陷。

叠放的规矩：一张牌下面可以叠多张；一张牌身上只挂一处；
一张牌不能压在自己身上。拖到空白处是拿下来，拖到画面左下角弃牌堆是丢弃。

房屋三级：棚 = 柴 + 田垄（每轮多保留 2 张）、屋 = 棚 + 2 石（+5）、仓 = 屋 + 2 泉（+10）。
房屋本身不产出，也能被别人叠上去。住满 2 人之后每 60 步出 1 个人，
生出来就是成人，一步开始吃一份。

牌位上限的读法：它是一轮进食结算后能保留几张牌，不是桌面上能同时放几张。
轮末之前可以超过，到结算那一刻超出的部分要处置掉 —— 它压的是玩家的选择，不是玩家的手。
基础上限 6，场上每张房屋牌往上加。开局 7 张牌，所以开局就超一张，
第一轮结算强制处置至少一张，第一轮就把这条规则教给玩家。
处置走弃牌堆；弃牌堆是轮末强制处置的执行口，不是「牌位满了放不下」的出路。
上限与当前张数都进快照，每轮报「超了几张」。
这一轮不加牌，玩家的牌只减不增（合成 2 换 1、丢弃 -1），
所以这个上限只会在第一轮咬人，之后永远超不到。见待确认区。

配方表吃任意份输入，键是无序多重集：输入按牌种计数，不按次序。
房屋那三条配方都是三份输入，「同种两输入」只是其中一种退化情形，不单独特判。

时间：局内唯一单位是步。逻辑每推进一步 = 0.1 秒（→ 「时间基准」）。产出与扣除都按步发生，不攒到结算点——玩家要能看见数字在爬。每 60 步结算一次进食，供不上的人死。
空格暂停只冻时间轴，不改变结算点，暂停期间照样能拖、能叠、能拆。

## 验证命题

没有叙事、只留堆叠与时间，这个循环成不成立。时间驱动产生的是决策，还是只有压力。

## 生死线

1. **发现**。三个未接触过的真人，无引导试玩，结束前每人至少合出三张事先不知道存在的牌。
2. **决策**。同一批试玩里，三人中有两人在进食缺口出现后主动改变过绑定关系。

三人中至少两人同时满足两条，判绿。

这两条走真人试玩，不用逻辑层测试去假装验。测试能盖住状态，盖不住「玩家会不会主动改绑定」这种命题。

### 判绿流程

1. 找三个没玩过的人，只说规则不说配方。
2. 录屏，不提示。
3. 事后逐人口述：你怎么发现那条配方的。
4. 口述里出现「试出来」而不是「看懂」，发现那条算成立。
5. 缺口出现后有没有主动改绑定，看录屏里的绑定关系有没有变过。

操作步骤与判读表见 [`试玩手册.md`](试玩手册.md)。

### 当前状态：**待验**

八片 agent 可做的都做完了（63 条逻辑层断言全绿、真机点选与注入同结果、出图复核过），
但上面两条一条都还没被验证过 —— 测试能证明绑定关系变了，
证明不了是人主动决定变的。判绿或判红要三个真人跑一遍。
结论落回本栏，把「待验」改成判绿或判红，并附上三人分别的情况。

### 实现时改掉的一处原始设计

原写法是「结算点判进食、发死亡」，进食的**扣除**也在结算点。
实测发现那样会与逐步扣除重复扣同一顿饭（账立刻对不上），
所以改成：扣除逐步发生（每人每步一份，先到先得，扣不到记成欠账），
结算点只判「谁这一轮欠着、谁死」。这一轮吃掉多少由逐步扣除累计而来，
所以「吃掉多少」与「欠了多少」是同一本账的两头。

连带的一条：一份食物先到先得（按登记次序发）。这个次序不是随手挑的 ——
它让「有人这一轮吃满了、有人没吃满」真的可能发生；
若改成每人每步各吃一份，食物不够时每个人都欠一样多，
「供不上的人死」会退化成「所有人都死」，「只有欠着的人死」这一句就没有对象了。

## 框架复用与缺口

### 能直接复用

| 能力 | 位置 | 用在哪 |
|---|---|---|
| 步进与暂停 | `Scheduling/GameClock.cs:144` `Advance(int steps)` | 按步结算 |
| 注入动词注册 | `DebugBridge/DebugConsole.cs:47` `Attach` | 「把 A 叠到 B 上」直达 |
| 牌的身份与序号 | `Entities/EntityCore.cs:145` `Spawn` / `:234` `Remove` | 每张牌一个实例 |
| 菜单栈 | `FrontEnd/FrontEndLayer.cs` | 标题屏与暂停屏 |

### 原型侧要自己写的三块

1. **绑定关系**。建造层表达不了：它只认世界坐标加占位，没有引用字段（`Construction/ConstructionCore.cs:64-105` 册上一行没有父指针）。原型侧做成独立模块加明确 seam，成熟了再考虑收编 GugaFramework。收编判据是产物进不进最终包，不是「这次用到了」。
2. **按步产出一个数**。建造层只到完工事件，没有按步发的产出件。
3. **叠放交互**。全仓零拖放代码——`GetDragData` / `_CanDropData` / `DragAndDrop` 一次都没命中。
   第一版用点选两步（先点一张，再点另一张）。第二轮换成拖放：
   自由平面上拖一张压到另一张上，点选从界面下架，桥上的 `click_card` 留给 agent。
   spec 在 `.scratch/stacklands-benchmark/`。

### 实体层两处注意

- 牌的载荷不进快照段（`Entities/EntityCore.cs:376-378`）。牌的自有字段要原型自己印一段。
- 事件默认容量 256（`Entities/EntityCore.cs:32`）。大批量销毁要显式抬高。

## 逻辑层接缝与快照口径

一个接缝：`DebugSnapshot()` 读，`Place` / `Bind` / `Unbind` / `Combine` / `Advance` 写。

快照一段一行，段用 `|` 分。段首依次是 `tick=` / `card count=` / `bind count=` / `ration ` / `recipe count=`（2026-10-13 真机读数）：

```
tick=0 seed=20260930 | card count=7 issued=7 nextseq=8 dropped=0 C c01 seq=1 kind=Wood every=4 out=0 livedin=- … C c07 seq=7 kind=Spring every=3 out=0 livedin=- keep=6 over=1 | bind count=0 | ration food=5 owe=0 alive=3 next=60 settled=0 ate=0 dropped=0 H h1 owe=0 ate=0 H h2 owe=0 ate=0 H h3 owe=0 ate=0 | recipe count=9 recipe 0 2 Wood Stone => Spring …
```

- **保留上限与当前张数落在牌段**：`card count=` 那一行末尾的 `keep=` 与 `over=`。开局 7 张、基础上限 6，所以读数是 `keep=6 over=1`。
- **挂接段每行带一个类型标记**：住户是 `B c11 onto=c19 kind=Resident every=0 in=0 out=0`，产线是 `B c14 onto=c13 kind=Production every=15 in=1 out=9`。`kind=` 是唯一说得出「这一条是产线还是住户」的地方。
- **房屋住读数也落在牌段**：`home c19 live=2 born=0 in=1`。场上没有房屋牌时这一段一个字都不加。
- **牌是实体层的一个实例**：id、序号、增删次序走 `EntityCore`；牌的自有字段（类别名、产出间隔、累计产出、曾住在谁身上）由 `CardBook` 自己印一段。实体层事件容量构造时抬到 2048。
- **绑定关系自建模块**：不进建造层（`docs/adr/0017`）。一张牌只压在一张牌下面，但它下面可以压多张。
- **按步连续**：产出与扣除都逐步发生；结算点只判「谁欠着、谁死」，不重复扣饭。

## 术语

**牌**：可堆叠的物件。运行中是一个实例，可被消耗，可被叠到另一个牌上。与兵种侧的「卡」同名不同域。

**产线**：一张牌叠在产粮牌上的那条关系，上面那张按自己的间隔产食物。

**住户**：一张牌叠在房屋牌上的那条关系，占房屋一个空位。住户不产食物。
两种关系记在同一份表里，每条带一个类型标记。

**牌位**：一轮进食结算后能保留多少张牌。基础上限 6，每张房屋牌往上加 2 / 5 / 10。
轮末之前可以超过，结算那一刻超出的部分要处置掉。

## 待确认区

- **生死线判绿还是判红**：待三个真人试玩，材料见 [`试玩手册.md`](试玩手册.md)。
- 灰盒阶段的牌用什么呈现。第一版是 UI 矩形色块（`Scripts/CardTable.cs`）；
  第二轮改成卡牌外观（圆角、描边、投影、顶部进度条槽），仍是色块，不走真模型。
  2026-10-13 复核：这一轮做的是卡牌外观，不是真模型，牌走不走造型线仍欠着。
- 牌集规模。第一版 6 牌种 / 6 配方是按「BFS 能试出 ≥3 种新牌」定的机械下限；
  第二轮加三种房屋牌与三条房屋配方，配方表扩到任意份输入。
  `BalanceTests` 已按新配方表重跑：可达牌集 26 → 35，
  稳态产出上限仍是 2.361 份/步（1 柴 + 1 石 + 2 夜露瓶），
  房屋牌间隔为 0 不产食物，所以它给不出更高的数。
  够不够三个人各发现三次要试玩才知道。
- 牌位上限的数值。基础上限定 6，三级房屋的加成是 +2 / +5 / +10，在配方里。
  真跑起来之后要看「第一次轮末被迫处置发生在第几步」，那属于试玩观测。
  这一轮不加牌，玩家的牌只减不增，所以这个上限只会在第一轮咬人、之后永远超不到。
  这一条如实记着，不是漏了 —— 加牌的路写在 spec「Out of Scope」，是这一轮的范围之外。
- 开局牌序只喂得饱两个人还是三个人：稳态产出上限 2.361 份/步，两个人每步吃 2.0 份所以站得住，三个人每步吃 3.0 份所以吃不饱，第一轮结算至少死一个人。数字口径是玩法决定，等用户拍板。
