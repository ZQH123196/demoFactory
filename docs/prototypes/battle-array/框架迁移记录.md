## 7 第七期：排兵布阵接入 —— 场地与激活检查落地，退休那一格卡在末位差（寻路层，工单 08）

### 7.1 落了哪几件

`BattleNavGrid.cs`（场地注册口：竞技场 ±12 米收成 24×24 格、1 米一格、格长与卡表钉在一起、坐标换算）、`BattleNavMove.cs`（走位那一半：三个命令、只读移动解、把技能层定身包成 `NavMoveCheck`）、`BattleAbilities.cs`（激活检查那一口，转发 `AbilityStepper.CanMove`，原型不另判一次）。`BattleWorld.cs` 的 `StepToward` 与 `SeparateSameSide` 退休——退休与摘豁免是同一发。

### 7.2 格长定档：1.0 米，保守量实测 1.2171027843833055 米

| 项 | 值 |
|---|---|
| 格长 | **1.0 米**（24×24 = 576 格），边界与 `ArenaHalfWidth` 对齐 |
| 每步子步数 | 0.12 / 0.14 / 0.15 / 0.32 米都只切 1 份 ⇒ 子步在本场是空转 |
| 最大保守量 | **1.2171027843833055 米**，扫 106040 个点，上界 √2 ≈ 1.4142 |
| 布阵最远点净空下界 | **1.013845853834198**（世界 z = 11.35）> 骑手半径 0.75 ⇒「半径进净空」咬不到 |

**档与表钉死两边各校验一道**：层侧「格长为正、为有限数」，宿主侧三条——格数 × 格长 == 边长、格长 ≥ 最大每步位移、最大半径 ≤ 最远格净空下界。任一条漂了当场抛。

**一个 float 残差**：`SpeedOf(骑手) × StepSeconds` 升成 double 是 **0.32000000953674324**，不是 0.32。用例照实钉住这个逐字值——钉四舍五入后的数等于把残差藏起来。

### 7.3 末位差：判据从「逐字相同」改成「判定没被偷换」

前置账的「全可走地形上逐步位移逐字相同」被实测否掉：语义相同、算术精度不同（旧路 `float`，寻路层 `double`）。坦克 1.2 米每秒第 3 步首次分叉，典型差 4.77e-07 ~ 9.54e-07 米，1200 步最大差 **2.384185791015625E-06 米**。新路给的是更干净的那个数。

**用户裁决**：接受末位差、退休旧路 float。**判据随之换掉** —— 不再比逐字位置，改比判定：射程、首次进射程那一步、够不够得着翻转次数、终局血量四项新旧一致。

末位差在实战里会放大：15v15 一局 30 个单位贴身互推，第 1 步起每个坐标就差 1 个 float ulp。**拿零回归对照读数前，先看样本里有几个贴身单位。**

### 7.4 层开了三个口

| 口 | 层里那一处 | 它写什么 |
|---|---|---|
| 落位移 | `NavStepper.ApplyMove` | 位置与朝向两列立刻改，其余列一个字不动 |
| 参与标记 | `NavStepper.SetCountedInSeparation` | 记成 `false` 的那一个两头都不参与——既不被推开，也不推别人 |
| 每步移速标量 | `NavStepper.SetMoveSpeed` | 换成宿主此刻的绝对数 |

落位移不夹取也不判界：给在哪就是哪，界外落点下一次求解照实报 `地形无路`。参与标记那列只管避让，不管能不能动。每步移速标量口**已结——保留**（用户确认）：没有它，踏地减速与盾墙加速就不再影响走位。

### 7.5 激活检查调用顺序

先问允不允许动，再算站哪。`BuildActivationCheck` 把 `CanMove` 包成 `NavMoveCheckVerdict`，`NavStepper` 在求解之前问一次。拒了交出 `HeldByActivationCheck` + `激活检查 定身`，不静默跳过。

递的是「此刻挂着谁」那个口而不是实例——技能层接在世界构造之后，按实例递会永远拿到 null，症状是「定身挂上了却还能走」。名字带 `Of` 后缀而不是重载。

### 7.6 豁免名单：排兵布阵那两条摘掉了，剩 4 条

摘豁免与退休方法是同一发（摘了豁免守卫当场判红）。守卫断言「命中数 == 豁免条数」改成跟着名单走——写死一个数正是那条断言要防的动作。第九期清到空表。

### 7.7 判绿线回归与它的定位

**现象**：退休手写趋近后，摆位对照判绿线从 167/200（CI [77.7%, 88.0%]）掉到 141/200（CI [63.8%, 76.4%]），两区间不重叠。

**这一节要留下的是方法，不是结论**：

1. **扰动对照臂**判「噪声还是真回归」。给旧路加一个 ε：1e-5 起分叉，1e-1 时 573/600 逐局不同，统计量仍 166/200 且 CI 与基线重叠 ⇒ 那 13 个点不是这条统计量对扰动敏感。
2. **每条假设做成「能证伪的扰动臂」**，不是修复版。改完跑出来与对照臂一样，只说明这一处改不改都一样。
3. **每臂带阳性对照**，否则 `0/600` 分不清「真无效」与「夹具没生效」。
4. **先立同口径再比较**。拿旧码「分离前」减新码「避让后」会得出无意义的数；同口径一立，结论就反转。

**已排除的**（每条有一臂撑着）：参与标记晚了一步、镜像同步点、配对序、追实体目标源、身体半径口径、网格量化、激活检查与边界。「够得着就吸附」那一档为什么是死的：出手判定距离 ≈ 2.8 米，追兵在两米开外就停手，**永远进不了「距离 ≤ 一步」那一档**——读一处分支前先量它有没有被走到。

**附带真发现**：分离的配对序是承重的。反转登记序后 20 局口径翻回 `Matters`。真语义敏感，但量级不足以解释那 13 个点。

**根因**：`BattleWorld.Step` 那个 `switch (decision.Intent)` 漏了 `Hold` ⇒ 这一趟不发令 ⇒ 单位留着上一步的命令。退休前「不发令」天然等于「站着不动」，迁到「命令由寻路层持有」之后两者不再等价。读数指纹三条同时出现：命令是 `Hold` 却走满步、状态 `Moving`、`卡住=Crowded`，驻守点连续几步逐字不变。**修法是补一行**；补这一行的消融臂跑出 167/200，与退休前基线逐字相同。

**教训**：「读数变了」有两种可能——底层语义真的变了，或上层某个分支漏了。先定位再重录；重录过的东西要逐项复测再决定改不改回去。有一类重录改不回去：那几处残差由测试每次跑都重写，复测后它们自己变回当前那一版。

## 第二个原型上树（BattleArray M5）：一棵树八个参数档、同步问、三处新事实（行为树）

同一棵树（`Scenes/_BattleBrain.tscn`：`SelectorReactive` 到 `Strike`/`CloseIn`/`Hold` 三条 C# 叶子）配八份兵种参数档（`Scenes/Brains/<模型名>.tscn`，各自 instance 那棵树、只覆盖 `range_override` 与 `brain_label`），30 个兵一人一棵。

1. **同步问，不等下一步**。无限领主是「宿主收 `Stepped` → 树写意图 → 世界下一步执行」；排兵布阵是世界在同一步里回头问树（`BattleWorld.Brain` 委托口子，桥 `Call("tick_for_bridge")` → 叶子认账 → 当场拿回决策执行）。这么换是因为 M4 的判绿建立在「离线跑与运行时逐字同一局」上，同步问就没有「哪一步的意图被哪一步执行」这本二次账。
2. **规则只有一份，叶子只搬参数**。`Logic/BattleBrainPolicy.cs` 是纯 C# 四档规则（没人→站、够不着→赶路、冷却没好→等、否则→出手），`BattleWorld.Step` 与三条叶子调同一个函数。叶子自己再写一遍距离判断，离线与运行时就成了两套真值。验证：首刀第 43 步、13 刀第 163 步，30/33 条测试全绿，headless 判定行与离线报告逐字同（第 27.9 秒 PlayerVictory，我方阵亡 11、敌方阵亡 15）。
3. **参数档与数据表钉在一起**。射程住在两处：`UnitCards`（进 `dotnet test`）与 `<兵种>.tscn`（运行时叶子真读的）。两道校验：离线 `BrainSceneParamTests` 逐字解析八份档，不等于兵种卡就红；运行时宿主 `_report_params()` 比对，漂了 `push_error("参数冲突 | ...")`。实测两道都有效：把 `HumanTank.tscn` 的射程从 1.6 改成 3.0（逻辑层一行没动），判定从 27.9 秒变 29.9 秒、我方阵亡 11 变 14，同时 30 条参数冲突告警刷屏。

**headless 跑带树的原型，日志里有约 90 条噪声不是故障**：`ERROR: Can't send message. No active debugger`。来源是 vendored `beehave_tree.gd:139` 无条件调 `BeehaveDebuggerMessages.register_tree(...)`，而 `can_send_message()` 的条件是 `not Engine.is_editor_hint() and OS.has_feature("editor")`——用编辑器二进制 `--headless` 直跑游戏时这条为真、调试器会话却不在，于是每棵树发送失败（`_ready` 一次、`interrupt` 一次，30 棵树约 90 条）。导出构建不响。

### 判据抓不到的一类

**方法实参里的中文**。`MakeRowLabel("兵源（拖到格子上…）", 20)` 这种文本经函数参数进去，不在 `.Text =` 右值位，静态扫不到。排兵布阵有两处是这样漏掉的。

### 踩到的坑：手写 `.translation` 二进制，引擎不认

曾自己写过一个编码器（「GDST」魔数 + 长度前缀），产物引擎直接拒：`ERROR: Unrecognized binary resource file: 'res://.../battlearray.en.translation'`。真格式是 ResourceLoader 的二进制资源（`RSRC` 头 + `OptimizedTranslation` + 哈希桶 + 字符串池）。编码器已删，`.translation` 全由引擎的 CSV 导入器产出。

### 长度压力测试：长文撑破布局

往 `battlearray.csv` 的 en 列填约 3 倍长的英文（占位符原样保留），重导入，切 `set_locale --locale en`，出图看布局撑不撑。**结论：撑破了。** 排兵布阵的 `DeployPanel` 声明高 372（`Arrange()` 里写死），长文下 `GetCombinedMinimumSize` 量到高 **696**。中文下同样这两行标签量到 133 + 101 = 234，落在 372 内——**中文布局本身是好的，破的是「按中文长度写死的面板高度」**。读数坑：`Control.Size` 与 `GetCombinedMinimumSize()` 在 `set_locale` 之后不立刻更新，要等一次布局（实测切语言前后都读回 `133 | 101`）。布局结论以**出图**为准。

| `BattleWorld.cs` | `new NavTerrainLink(` | `Assembly.AttachTerrain(BattleRoadblock.ToNavCell)` |

`BattleNavMove.Grid` 留着没删：`NavStepper` 不公开网格（只有 `NavSolver.Space.Grid`），而地形接线要落在装配存的那一张上。

### 真的复现了：镜像同步漏退订

迁前 `BattleWorld.OnDispose` 只摘了地形接线与 `Step`，`BattleNavMove.Detach()` 没人调 —— `NavStepper.OnPulse` 与 `SyncAllMirrors` 两条留在时钟上。**这一条是实跑复现的，不是从代码读出来的。**

场景：种 1001、默认阵 → `Advance(50)` → `Dispose()` → `Clock.Advance(200)` → 再读一次 `DebugSnapshot()`。

| 读数 | 值 |
|---|---|
| 释放前 `p02`（还在追人） | `(-1.1472327,1.5822434)` |
| 释放后再推 200 步的 `p02` | `(-1.1507227,1.6562086)` |
| 同一局里 `p01`（已在射程、原地出手） | 一个数都没动 |
| 同一局里 `p03`（已阵亡） | 一个数都没动 |
| 迁移后快照逐行不同的行数 | **0**（头部那两格时钟读数除外） |

症状只出在「还在追人」的那几个身上，与漏退订的形状一致。修法是构造里一句 `TrackDetach(_navMove.Detach)`；`OnDispose` 现在是空的（脉冲与走位那半归基类那张退订表，地形接线与走位流水线归 `Assembly.Detach()`）。

### 比状态不比步号：头部归时钟的是两格

「释放后快照逐字不变」按字面写不成立：`Dispose` 交还的是订阅，不是时钟 —— `Clock` 是公开读数口，那 200 步真的走过去了（步号照涨，步号另立一格断言）。快照头部**两格**归时钟（`tick=` 与 `seconds=`），都要去掉再比；头部剩下的 `phase` / `outcome` / `ours` / `theirs` 留着逐字比。

另配一份没释放的对照世界，在同一段步里确实变了 —— 没有这一半，「不变」那条在「什么都没订阅」时也成立，不是判据。

### 统一推进次序对这一局是恒等

`WorldAssembly.Advance` 每步的次序是「落地形 → 推时钟 → 推建造」。排兵布阵全部蓝图 `BattleRoadblock.BuildDurationTicks = 0`，`ConstructionCore.Countdown` 在进度不变时直接返回、不发一条事件 —— 第三段对这一局是恒等操作。迁移前后既有 251 条（249 过 2 跳过）一条没改，本 ticket另加 2 条装配与退订的用例。

### 四份 L3 基线被重录过（不是基线漂移，是行为变更）

**这一格必须单独写出来**，因为「测试全绿」在这里的含义与别处不同：绿的代价是四份入库基线被改写了。

真因在 `DuelRiftSetup.cs:139-150` 那一段：旧的推进循环用 `world.AdvanceDebugSteps(...)`，

### `Step` 开头那行 `_terrain.Pump()` 留着

统一推进次序那一处推这一步之前已经泵过一次，工单说这一行「已成冗余」。留着有两个理由：三个调试口中的 `AdvanceOneDebugStep` 与 `AdvanceDebugSteps` 是直接推时钟的、绕开那一处（`AdvanceUntilEnd` 走 `Advance(1)`，不绕开）；多泵一次是幂等的 —— 没有待读事件时它直接返回，不动网格、不进 `Missed`。

### 结算屏并进公共层

`BattleHud` 那一块结算面板删掉（`_resultPanel` / `_resultLine` / `BuildResultPanel` / `ShowResult` / `HideResult`）。HUD 留棋盘与阵面读数（顶行那一句「已判定 · 第 x 秒 · 双方存活」、钱、兵源、暂停钮）—— 那些是玩法内容不是结算屏；结算那一句与双方阵亡并进前端层的结算屏明细。
