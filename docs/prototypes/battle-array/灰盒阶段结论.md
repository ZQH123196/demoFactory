# 排兵布阵（BattleArray）— 灰盒阶段结论

> 本文只留事实、机制与实测数字，约束句引契约名。逻辑一步 = 0.1 秒。几何数字在 `model-review.md`，数值表在 `design.md`。

## 骨架（不算工作包）

自 `_Template/` 复制，公共层零改动。坑：编辑器开着 `cp -r` 会把 `.cs.uid` 一起复制，两份资源撞同一身份；复制后删伴随文件让编辑器重生成。

## M0 / M1 已完成

M1 用探针 `HumanWarrior` 接通造型线，六步全绿且重跑 md5 全等。造型线是六步：`gen` → `check` → `export` → `import` → `inspect` → `review`；无头 `--script` 进程不跑导入流水线，删净重跑报 `FAIL HumanWarrior.glb 加载失败`。M0 契约的数字全在 `design.md`「M0 契约」三节。删净重跑 `HumanWarrior.glb` 前后 md5 均为 `e62c460a3a965dc487638d2c49e5b6ed`；`.glb.import` 的 `[remap] uid` 每次首次导入随机发，所以伴随文件入库。

## M2 / M3 已完成

体检单 8 PASS 0 FAIL，两次重跑 139 个产物文件 md5 全等。M2/M3 红了只拖累观感 —— 判创意的是 M4。

## M4 已完成 —— 判绿：摆位有因果力，创意地基成立

判绿线跑之前登记：「阵亡差 ≥ 1.5 兵」且「同种子配对同向 ≥ 15/20」；判红线是「差 < 0.5 兵或同向 < 12/20」。

### 对照跑数字（每种摆法 20 局；敌方固定常规摆法、与我方镜像同阵容）

已由《M8 已完成》重测取代：平均阵亡差 **3.85** 兵、同向 **19/20**。旧口径三档胜率 95% / 65% / 40%；好处 18 秒才分岔 ⇒ 不是开局领先，是「谁的后排先死」。

### 三条必须如实记的发现（第 2、3 条要用户裁决）

1. **「M0 契约」的数字全部自洽**：近战 1v1 首刀第 43 步、第 163 步见血收，与手算逐字一致。
2. **「一局 10 分钟」不成立**：满编 15v15 实测 20~31 秒打完。已裁决接受短局：上限 120 秒、到点判赢，开局记账点 30 秒 → 第 12 秒。
3. **有因果力 ≠ 有取舍**：同阵容同摆法必判「同尽」，而「弓手夹中间」打出 95% 胜率 ⇒ 存在近乎必胜的摆法。

### 落地的三处工程口径（后来人别改回去）

- **同步结算消先后手**：本步所有出手在决策阶段声明、结算阶段同时扣血。
- **扣「承伤」不扣「出招伤害」**：目标只剩 4 血时那一刀也只记 4 ⇒ 守恒账闭合。
- **抖动是样本量的来源**：入场位置 ±0.35 米、移速 ±8%、攻击间隔 ±1 步；台账 `jitter: false`，对照 `jitter: true`。

### 观测口现状（三个观测口里 M4 带来的两件）

状态可查：`DebugSnapshot()` 一发读全量真值，每兵带 `why=`。已由《M6 已完成》补齐取代。

## M6 已完成 —— 布阵网格 UI、随时暂停、三个观测口补齐

`DeploymentBoard.cs`（15 格、单价与名义额度、摆子 / 撤子 / 挪位三条写入口、拒绝必带理由）与 `BattlePhase`（布阵→战斗→已判定）；调试桥接线收编进公共层 `DebugConsole.cs`，本原型接 18 个动词。默认停在布阵期，带 `BATTLE_ARRAY_AUTO_START=1` 或 `++auto-start` 才一进来就开打。

### 三条要验的逐条对完

- **摆子直达口能把一个兵放到指定格**：`place --kind rider --row 2 --column 0` → 「已把骑兵（rider）摆到 第3排 第1列（花 150，剩 530）」；往同格再摆 → 拒（「一格只站一个兵」）。
- **暂停时读出一句「谁为什么不动」**：`toggle_pause` 念「e07「劫掠者」敌方……最近的活人是 p07「剑士」，隔 2.47 米（够得着的距离 2.70 米）｜为什么：在射程内、冷却剩 8 步」，同一句在出图帧的屏幕底部读得出。
- **MCP 实测截图 + 注入直达口**：注入这一半 ✅；截图那一半走 `--write-movie`，**MCP 那条通道仍欠一次**。

### 运行时实测数字

布阵期推 600 步步号仍 0、快照逐字不变；棋盘摆子与直接递摆法的快照逐字全等；两次 headless 全日志各 1292 行 `cmp` 全等；`restart` 后 `brain` 仍报 `brains=30/30`。`SCRIPT ERROR` 0。

### 运行时实测抓出来并修掉的四处（都是「读出来才知道」的观测缺陷）

1. **阵亡者记不出死因**：`KilledById` 从 M4 起就没被写过，读数念「阵亡（未知击杀）」。
2. **布阵期的 `why=` 念成「对面已无人」**：那是「还没问过打谁」，改成「布阵期还没开打」。
3. **暂停中单步口空转**：新增 `AdvanceOneDebugStep` —— 临时解冻、推一步、再冻回去。
4. **判定之后时间轴照推**：HUD 念「第 164.9 秒」而仗在 27.9 秒打完 ⇒ 判定时冻住 ＋ HUD 分三档读数。

### HUD 布局的一处引擎事实

`CanvasLayer` 直下的 `Control` 用锚点预设算不出可靠父级尺寸：`BottomWide` 那条算出**负宽高**，暂停读数被挤成一列竖排的字。改成照 `GetViewport().GetVisibleRect().Size` 排绝对坐标 ＋ `SizeChanged` 重排。

### 公共层两处（AGENTS「沉淀方向」那条反哺线）

`DebugConsole.Attach(parent, globals, verbs)` 把每个原型都要重抄的那 15 行收编，原型只递**自己的写入口**；`_Template/Scripts/Main.cs` 自带桥接线样板。

## M7 已完成 —— 配比有因果力，但买兵不用看对面：有一档通吃

量法：五档配比 × 三组敌方阵容 × 20 粒固定种子 ＝ **300 场**，每档都按**同一个排布函数**入场。

### 胜率表（每格 20 局，我方视角）

五档（均衡 4坦4战4弓3骑 / 盾墙 7坦4战4弓 / 弓手海 3坦2战8弓2骑 / 骑潮 2坦2战3弓8骑 / 近战重锤 5坦8战2弓）对三组敌方阵容（均衡 4/4/4/3、弓手海 3/2/8/2、骑潮 2/2/3/8）的胜率跨度 **0% ~ 100%**；近战重锤三组全 **100%**，骑潮三组最差（0% / 10% / 55%）。**300 场没有一局靠 120 秒兜底判赢**。

### 我方平均阵亡（越少越好；「要不要看对面」看的是这一列的排序会不会换人）

按上面三组敌方阵容的列序：均衡 11.85 / 10.65 / 7.10；盾墙 11.40 / 10.35 / 6.70；弓手海 13.90 / 12.75 / 8.10；骑潮 15.00 / 14.60 / 12.25；近战重锤 9.00 / 9.35 / 7.25。

### 三条结论

1. **配比有因果力**：换配比能把胜率从 0% 拉到 100%，远超跑之前登记的「有差」线（15 个百分点 / 1.5 兵）。
2. **但「买兵必须先看对面」没成立**：近战重锤三组全 100% 胜 ⇒ 存在一档通吃，裁决落在 `OneBestAnswer`；骑潮三组最差 ⇒ 这一维有明确的坏选择，却没有「看对面再决定」的结构。
3. **M4 那句「有因果力 ≠ 有取舍」在配比这一维重演了**：**地基成立、取舍未成立**；要不要把「买兵必须看对面」做出来是一条待确认项。

### 这三条结论的适用面（外推之前先读这一条）

五档与三组都是挑的样本，不是穷举 ⇒ 结论只在这 5×3 内成立；敌方不会用「弓手夹中间」那类非对称摆法。

### 判绿跑完之后改了一次，这件事如实记在这里

第一版「最优配比」用**单一尺**（胜率先比、平手比阵亡），盾墙靠阵亡少 0.55 兵被挑成「最优」，裁决于是报成买兵要先看对面 —— 量具与问题对不上。后来收紧成「按胜率的并列最优集合在三组里求交集」，收紧后同一批 300 场给出 `OneBestAnswer`；**没有改的是阈值**。

### 归因地基照旧成立

五档 × 同一档自己打自己（关抖动）**全部判同尽** ⇒ 排布函数与机制都不偏袒先后手；五档每一档都买得起（最贵的骑潮 1880 ≤ 初始额度 2250）。

### 这套量具已经删掉了（2026-09-26 用户令）

`CompositionComparison.cs` 与 `CompositionComparisonTests.cs` 已整份删除；上面三条结论按删除前那一次跑为准，代码与报告在 git 历史里。删除理由不是运行成本，是用户不认这套矩阵问法。

## M8 已完成 —— 两条种族规则落到数据、逻辑层零种族分支；量级上「力大」压过「手长」

规则住进 `UnitCards.RaceRules`，**八行登记表一个字没改**。**逻辑层结构性改动＝0**：新测试逐字扫 `Scripts/ AI/ UI/ Tools/` 全部 `.cs`/`.gd`，允许名单只有三份数据文件。人族四档射程 → **1.76/1.98/9.9/2.2**，兽人四档不动；故意把 `HumanArcher.tscn` 漂成 8.0 ⇒ 离线那条当场红、headless 跑出 **4 行** `参数冲突`。

**规则到底进没进结算**（四条都是量出来的）：只换对面那一族，同族镜像胜率 **70%** → 对面换兽人 **15%**（挪 55 个百分点 ⇒ 两条 ×1.1 不等价，攻击那条明显压过射程那条，我方均阵亡 13.15 → 14.60、敌方 14.35 → 12.55）；异族镜像三档摆法**全部不再判同尽**而同族镜像三档**仍全部同尽** ⇒「机制不偏袒先后手」没塌，数值只有一处真值（逐兵钉 `Card ＝ Look.Stats`）；运行时 `snapshot_debug` 读得出 `p11 弓手 atk=16 rng=9.9`，盾卫隔 2.82 米出手而基准表口径是 2.65 米 ⇒ 1.76 那条生效了。

**量具换了一格控制变量，但没换问题**：两族各带一条规则之后「敌我镜像必判同尽」问不到问题了 —— 不同族的镜像本来就该分胜负。口径改成对照跑两侧**钉在同一族**（`同族镜像同摆法必判同尽` / `异族镜像同摆法必分胜负` 各钉一侧）。**M4/M7 那两张表与两个裁决一个字没动**：摆位**仍判绿**（最优仍是「弓手夹中间」，平均阵亡差 3.85 兵、同向 19/20），配比**仍是「一档通吃」** ⇒ `OneBestAnswer` 不变。

**默认对阵变弱了**：运行时那一局从 M5/M6 记的 `第 27.9 秒 PlayerVictory 我方阵亡 11 敌方阵亡 15` 变成 `第 27.5 秒 PlayerDefeat 我方阵亡 15 敌方阵亡 12`⇒ **这套数值下默认对阵我方会输**，这条锚点从此由测试钉着。机制台账跟着挪两个数：首刀第 **42** 步、打死蛮牛第 **162** 步（M4 记的是 43 / 163）；剑士剩 **53** 血。

**本轮没验到的**：八件造型在两族数值分家后没重跑体检单（体检单出的是几何 / 胶卷 / 比例）。M8 是 M0~M8 的最后一包 ⇒ 没红 ⇒ **灰盒阶段收口**，下一步进活人感测试阶段（「游戏开发的各阶段」）。

## 三层铺设 批③ 已完成 —— 赛前路障接建造层（Q14 + Q7）

给建造层造一个真实需求（**赛前路障**），把路障那两条写路径补进 Journal。设计定稿在 `.scratch/三层铺设/spec.md`，机制在 `docs/GugaFramework/建造层.md`，收编账在本文档夹的 [`框架迁移记录.md`](框架迁移记录.md)。

### 路障那条蓝图

| 档 | 值 |
|---|---|
| 蓝图 id | `roadblock`（建筑 id 由模块按登记序发：b1、b2……） |
| 占地 | 单格网格放置（锚点 ＋ 无偏移），格长 1.0 米（与寻路网格同一档） |
| 方向 | 恒 0（八值编码的 rot0）：单格占地转哪个方向都占同一格 |
| 工期 | 0 步：放下那一刻就建成（事件流上连发 placed ＋ completed） |
| 血量 | 上限 5000（大值，占位读数：真掉过血一眼看得出来） |
| 模型引用 | 空串：**不渲染**（没有真模型就不画；画了就得走造型线四件套） |

**无攻击路径**：这一侧一条打建筑的写口都没接（扣血 / 修复 / 场地建筑登记都当场抛），整局打完它还是满血。

### 三条写路径与那个前置条件

`PlaceBuilding` / `RemoveBuilding` 是写路径（进 Journal），`CheckPlacement` 是只读查询（call 类，不入录）；只在布阵期摆得下与撤得动，开打之后两发都回 `ok=false + InvalidState` 并带那句人话理由（走 inject 的 `reason` 出口、不进 Journal），只读裁决与落建口读同一个前置条件。

### 接线：阻挡全部来自运行时放置

建造占用 → 寻路网格走 `NavTerrainLink` 的**网格侧**：路障的建造事件自带格名单（非空），两个查法都不用递；每步推进逻辑之前 `Pump` 一次，每一次写路径之后也 `Pump` 一次。

### 实测数字（离线段，新用例自己念出来的）

世界 (0,3) → 建造格 (0,3) → **寻路格 (12,15)**。印子：放一座 `StampedCount` **2**、移除后 **3**、同一格重摆后 **5**，`Missed` 全程 **0**；绕行基线扩展 **15** 格 / 格路 15，挡上之后 **18 / 15**，移除之后回到 **15 / 15**。

### 零回归读数

路障缺省零放置 ⇒ 既有逐字基线一个字都不用重录（`duel-rift-h3.json` **780B1299…**、`duel-rift-h3.level1.txt` **26B0E6FB…**、摆位对照报告 **35FC75A7…**）；摆位对照照旧判绿：平均阵亡差 **3.85** 兵、同向 **19/20** 局，60 局没有一局打满 120 秒。

### 这一包留下的待确认项

**路障不渲染**：表现（真模型 / 摆放预览 / 幽灵）留给垂直切片，见「待确认区」。

## 三层铺设 批③ 补录 —— 摆子口三动词进 Journal（Q7）

`place` / `remove` / `move` 三条本轮真接上（上一节只接了路障那两条）。

### 写路径落在哪

| 动词 | args | 落点 |
|---|---|---|
| `place` | `兵种\|行\|列` | `BattleWorld.PlaceUnit` → `DeploymentBoard.Place` |
| `remove` | `行\|列` | `BattleWorld.RemoveUnit` → `DeploymentBoard.Remove` |
| `move` | `从行\|从列\|到行\|到列` | `BattleWorld.MoveUnit` → `DeploymentBoard.Move` |

三条命令的入口只有一个：`MainReplayBridge.WriteDebug`（桥动词 `inject` 与三条动词、鼠标拖放与点格都走它）；在录就走 `ReplayAssembly.Inject`，没在录就直接打词表。

### 实测与零回归

三动词各录一发都 `ok=true`，开打之后 `place archer|2|0` 是 `ok=false`；重放端每发照录制复现，两跑检查点指纹逐字相同。BattleArray 245 → **251** 条全绿。

### 本轮留下的待确认项

- **宿主换新世界那一笔不在 Journal 里**：棋盘一变 `Main` 就换一份新世界（`OnBoardChanged`），那一笔没录；引擎里重放含摆子写路径的剧本，会话会因换局作废。
- **录制会话绑的是开录那一刻那个世界**：录制期间摆一手就换新世界，而 `ReplayAssembly` 还攥着旧世界。上面两条是同一个接缝（宿主与重放装配之间）。
- **摆子口那三个桥动词的返回文本换了形状**：从棋盘那一句人话换成 journal 读数加一行棋盘摘要；HUD 反馈跟着换字，未出图复核。

## 量级口径（本表的尺子，先定尺再打分）

| 维度 | 含义 | 档位 |
|---|---|---|
| **规模** | 文件与代码面 | S（≤3 文件）· M（一个子系统）· L（一整条线） |
| **难度** | 会不会卡住 | 低（照抄）· 中（有坑但坑已记账）· 高（结论可能推翻计划） |
| **量级** | 连续作业时长，单位＝**半天** | 锚点：无限领主 17 模型的工具线是一天级 |
| **红了影响谁** | 这一包失败时后面哪些包作废 | 越靠前越小 ＝ 越早能止损 |

**总盘 ≈ 10~11.5 个工作日**，其中能证伪这个创意的只有 M4（1 天）。实际花 10.5 天。

## 为什么这么排（三句真话）

模型先行的代价已经明码（M4 若红，8 套关节树要按新比例 / 占地返工）；M4 与 M1~M3 零依赖，纯逻辑包不需要任何 `.glb`，是全盘唯一的高风险包；`HumanRider` 是最贵的一条，所以放在人族最后一个留缓冲。

**为什么「摆位对照测试」排在逻辑层第一包**：摆位若没有因果力，M5~M8 全是在装修一个空壳；它判红就是本原型的**有效失败结论**，照样入库。
