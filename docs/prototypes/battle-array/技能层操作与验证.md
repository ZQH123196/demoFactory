# 技能层操作与验证 — 排兵布阵

> 这一份是排兵布阵技能层的工位用法与验证场地搭法（技能体检单、单挑场 H2、技能层的画面证据）。
> 技能层的实测结论在 `技能层验证记录.md`、等确认的在 `待确认区.md`，调研在 `docs/research/技能系统/`，
> 工具层的通道用法仍在《验证操作手册》。本文只留事实、机制与操作步骤。

### 单挑场 H2 怎么跑（纯离线，不起引擎）

技能层的三宿主里 **H2 全程离线**（它是开发期资产，不进游戏包）：

```bash
dotnet test src/Prototypes/BattleArray/Tests --filter "AbilityH2LedgerTests"   # 单挑场台账 22 条
```

- 场子本体 `Tests/SkillTestWorld.cs` 不认识任何技能：技能名 / tag / 属性名全在注册壳
  `Tests/SkillDuelRift.cs` 里 —— 这条分工有机器检查（断言 A50 直接去搜场子源码）。
- 写路径只有 `world.Inject(cmd, args)` 一发（与 H3 桥侧、CLI 同一条分发形状）；
  词表八条之外**现场扩了 `Move 单位Id|dx`**。`ResetWorld` 与 `Mark` **不在写路径里**：
  它们改的是「场子本身」，与「在场子里做事」不是同一条时间轴。
- 开局参数（敌方档位 / 敌血 / 我方档位 / 起始距离 / 随机）走 `Tuning` 记录，写进快照头部念出来；
  它们是**开局参数不是动词**，所以对照矩阵换档 ＝ 重开一场（`SkillTestWorld.Reset`），不是喂一条命令。
- **台账口径有一条要记牢：注入发生在两步之间。** 第 5 步之后按下的前摇 3 步技能，是在第 8 步过 commit
  （不是第 9 步）—— 手算在这里错过两次，每次都是这一格。

## 技能体检单 — 一条命令出一页三栏

**它把哪一步变便宜**：想知道「这 16 条技能各自的前摇 / 冷却 / 结算 / 效果到底是多少、顶住 GAS 哪一格、谁钉着它」，
从「翻三份文档 ＋ 在两张技能表里跳着读」变成「一条命令出一页，agent 读一页答完」。

```bash
G="C:/Users/.../Godot_v4.7.2-stable_mono_win64_console.exe"   # 找法三级同 `review`：--godot= > GODOT_BIN > PATH
dotnet run --project src/Tools -- skill BattleArray . --godot="$G"      # 出三栏 + 两道对表
dotnet run --project src/Tools -- skill BattleArray --selfcheck         # 只检查校验器本身（不起引擎、不读技能表）
```

实测：`skill BattleArray .` 一整发 **1.9 秒**（含 `dotnet run` 启动与无头读 8 个模型的 clip 时长）；
报告落 `docs/prototypes/battle-array/skill-review.md`（提交进版本库），时长表落 `.cache/Skill/<原型>/`（不提交）；
**连跑两次报告 md5 相同**。报告文字随判定改口而变、md5 跟着变，这是预期的。

四条操作口径（另六条与《验证操作手册》《模型与动画准则》重复，不在此重复）：

- **这一步可以无头**（与 `review` 唯一的区别）：只读骨骼与时长、不光栅化，走
  `godot --headless --path . --quit-after 120 --script res://src/GugaFramework/Tools/glb/inspect_model.gd -- --models-dir=... --facts=<绝对路径>`。
  `--facts=` 是机器可读出口，数字仍出自 `glb/model_metrics.gd` 那一份实现。两个工位共用同一个读取件
  `src/Tools/Facts.cs`；动过它之后跑一次 `review` 就能看到那条回归（`model-review.md` 与跑前 0 行差）。
- **报告是投影，不是第二份表**：栏 1 / 栏 2 的每个数字现取现排。所以「报告提交之后表又改了」这种漂只有测试能看见，
  钉子是 `Tests/AbilitySkillReviewTests.cs` 的 A76（逐格比前摇 / 冷却 / 射程 / 效果条数）与 A77
  （报告指的每个断言号都真在 `Tests/` 源码里；工具那两份源码里搜不到技能名 / tag 名 / clip 名）。
  ⇒ 改了技能表或改了断言名之后重跑一次 `skill` 再提交，不重跑的话提交的是旧报告，A76 会红在那里。
- **这道校验装在 `--selfcheck` 里**，不在 `dotnet test` 里（`src/Tools` 与测试项目不同程序集，
  看产物不看退出码 →《模型与动画准则》「窗口模式出图」）。**11 条合成读数**覆盖五种读数：
  对得上 / 动画比前摇短超半步**红** / 动画比前摇长**不判红但把超出量印出来** / 未挂号念不适用 / 挂号了读不到也红。
  改判红方向的时候两个方向都要在里面钉一条，别只留新那一头。

四条实测坑（**下次少走一步**）：

- **改一条 clip 的时长，必须连键帧时间一起改**：`clips_humanoid.gd` 里那个 `"length": d` 只是声明，
  导出后动画的**实际长度由末键的时刻兜住** —— 把 `d` 从 0.6 改成 0.1 而键还写在 0.2/0.35/0.5 秒上，
  无头读回来是 0.5 秒，体检单据此判「不红」，看着像对表失灵。要缩时长就把整段键帧按比例压。
- **新增 `.cs` 之后先 `--headless --import` 再跑工位**：`.godot` 脚本缓存过期会让 vendored 的 `.gd` 全部 Parse error
  （240 帧喷 6946 条，而世界静默走纯 C# 退路、`SCRIPT ERROR` 是 0）⇒ 一发 import 即清。
  同一个失效形状进《模型与动画准则》「出图与装配这条通道抓到的引擎事实」。
- **表现层要订事件，别按渲染帧采样状态**：起手动作第一版做成「每帧读 `CastingOf`、发现进入前摇就演」，
  桥一发 `advance --steps 300` 之后台账念「演 0 次」—— 2~3 步的前摇整个落在两个渲染帧之间，帧采样什么都看不见
  （快进、级 2 重放同理）。改成订技能层的 `activate` 事件之后一条不丢。断言 A78 腿 ② 钉着「必须事件驱动」，
  退回采样就红 —— 这是「事件发射前置」那句的实证版。
- **反证只能证明「它会红」，不能证明「它红得对」**：前摇对表第九轮装成 `Math.Abs(clip − 前摇) > 0.05 秒` 就红，
  当时那一发反证（挂号一条 1.0 秒的挥刀顶 0.3 秒前摇 ⇒ 红 ＋ 退出码 1）看着完全成立，
  实际证明的是「差得远就红」，而这一栏要防的只是「同一个数写两遍然后漂」—— 漂有害的那一侧是**动画比逻辑先演完**，
  反过来（动画多演一段）commit / 结算 / 冷却一格都不动，是合法表现层选择。结果这道防漂的机器把「把前摇演清楚」
  这条唯一通路堵了整整一天。⇒ 读完那几行实现、问一句「它到底要挡什么」，比再补一发反证值钱；
  判红的方向（单向还是双向、参与不参与退出码）要跟它的目的一句话对上，别默认「更严总没错」。

### 技能层的画面证据怎么摆

用户实看后的三句诊断，每句都对应一处便宜的口子（值得下一个接 H3 的原型照抄）：

| 看不见什么 | 补的口子 | 在哪 |
|---|---|---|
| 整场 17 米机位把 1v1 两个兵压成一小撮 | 单挑局**自动取景**：焦点落在活兵中间、距离按间距倒推（8~18 米、俯角 42°） | `Main.FrameDuelCamera` |
| 一局 14 秒就判完，来不及看清任何一次出手 | **演示档** `BATTLE_ARRAY_SHOWCASE=1`：两边血 ×3、给敌方也 `Grant` 一条主动；默认档一字不动，级 1/级 2 基线不背这本账 | `DuelRiftSetup.NewShowcaseWorld` |
| 前摇那 0.2~0.3 秒画面上什么都没有 | 头顶**施法读条**（进度 ＝ 已走步数 ÷ 表里的 `PreSteps`）；相位与总步数全问层，表现层不自判。走桥 `ability_snapshot` 读层自己那份真值 | `BattleAbilities.CastingOf`、`BattleUnitViews.MirrorAll` |

同轮把自动释放的口从「硬写那一条技能」改成「按栏位名的序挑第一条不在前摇也不在冷却的」——
只回答**先问哪条**，放不放行仍在 S4 激活检查判（实现只有一份）；身上只装突斩的那一局挑出来还是突斩。
