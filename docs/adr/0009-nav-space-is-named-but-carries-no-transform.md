# 寻路空间有名无变换：坐标相对空间原点，换算归宿主

寻路网格与路径都带一个 `SpaceId`，说明它们活在哪一个相对坐标系里；**空间本身不持有原点与变换，
不负责空间→世界的换算**——那一步归宿主，跨空间请求当场抛并带出双方 id。

网格自己可以带一个原点（`NavGridSpec.OriginX` / `NavGridSpec.OriginZ`）：说的是
「第 (0,0) 格那一角落在空间坐标的哪一点」，也就是**网格在空间里的位置**。
空间不持有换算，网格原点也不产生换算——网格挪位置是「宿主摆的场地在哪儿」，
空间→世界的换算是「承载平台在哪儿」；合成一件就是把双坐标系请回来了。

在移动的承载平台上（任何会走的载体、会动的局部空间）走的就是这条口径：
那张局部坐标的网格由宿主每一帧施加位移与偏航，本层一行不用改。这一条把
「局部坐标系与全局坐标系之间的换算」留在宿主侧，没有被本层请回来。

## Considered Options

- **只认世界系**：寻路网格活在世界坐标里。承载平台在动，那张网格要么每步按世界坐标重烘（烘不动），
  要么「会动的平台上那一格局部世界要寻路」永远做不了。
- **空间持有一个可移动的参考点**：路径在空间内有效，模块自己算空间→世界。那正是本仓当初
  判为「无先例、最贵」而避开的两套坐标系换算——为一个**已经被否两次**的情形请回全仓的账：
  跨空间追击被否，理由逐字是「会推翻这条坐标口径」；
  「怪物爬上甲板」这条本会成立跨空间追击的，做法是**在平台边缘就地生成**。
  它是**被设计掉的**，不是被推迟的。

## Consequences

- 空间移动时在手路径依然有效，变的只有渲染——模块这一侧不需要任何失效处理。
- 寻路层不留移动参考点，因此没有「参考点与网格不同步」这一类问题。
- 网格原点与空间→世界的换算是两件事：前者是场地条件（宿主递的两列，零基的网格递 0），
  后者是承载平台那件事（宿主施加位移与偏航）。
- 哪天真要做跨空间追击（双方单位在两只载体背上混战、怪物从大地图侧爬上甲板），
  「空间持有可移动参考点」是**局部增补**，不是推倒重来。
- 请求必须由宿主带上 `SpaceId`；漏带或跨空间混用一律当场抛，不静默换算。
