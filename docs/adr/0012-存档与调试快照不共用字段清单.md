# 存档与调试快照不共用字段清单

`src/GugaFramework/Persistence/` 与 `ReplaySnapshot()` 是两件东西，各写各的字段清单。
存档给机器读（下一次读回来），调试快照给人读（当场排查）。

## Considered Options

- **共用一份字段清单**（存档与快照从同一处取字段）：只有把调试和存档当成同一件事的人才会想到它。
  两者服务的是两种读者：调试快照要冗余、要带图例、要人读得懂；存档要短、要版本承诺、
  要机器读得回去。把它们焊在一份清单上，任何一边要改格式，另一边跟着动——
  而存档格式一发布就是承诺，改不动了。
  这个方案在这里连「成本合算」都不用算：想法本身不成立。
- **存档复用 `ReplaySnapshot()` 的文本**（实测 7 座建筑的单条快照 1288 字节，
  其中大半是 `treasury` / `outcome` / `图例 #地形阻挡` 这类给人看的词）：臃肿约四倍，
  且把调试格式变成了持久化承诺。不成立。
- **各写各的，接受权威状态被写两遍**：位置在宿主世界的单位段与
  `NavStepper.cs:877` 的寻路 agent行各有一份，两边都写。重复的是纯数据，
  而往返测试（`WriteState → ReadState → WriteState` 两串逐字相等）已经能抓到两份不一致。
  **如果 `WriteState` 与 `ReplaySnapshot` 对同一个状态算出两个值，那本身是个要修的 bug，
  而不是让存档迁就重放。** 本轮选这个。
- **抽单源，改造各世界的快照**：能让两边永远一致。代价是重录所有重放基线，
  而 `ReplaySnapshot()` 与 `DebugSnapshot()` 现在还是各自拼装、清单本来就没有单源
  （两处拼装点各写各的）。为一个还不存在的第二个消费者去动在用的三份基线，
  不划算。等真有一份第三方消费者时再说。

## Consequences

- 权威状态（金币、单位全集、建筑全集、旗全集、位置、技能账）在两处各有一份。
  往返测试守着存档那一侧，`VfxLedgerTests.cs:334-356` 那种反射扫出口的守卫守着「别长出第二套序列化」。
- 三分判据只对存档生效：权威状态存、派生数据不存（读档重算）、引擎句柄绝不存。
  调试快照不受它约束——它本来就该冗余，`NavGridSnapshot` 里存净空场是**有意的**，
  那张表不是第二份真值，而是「重放端有没有真的按同一套距离算法重算过」的独立凭据。
- 存档格式与调试格式各自演化，改一边不动另一边。代价是两套格式要各自维护——
  这正是选它的理由。
- 这一版不动 `ReplaySnapshot` / `DebugSnapshot` 的拼装，接受它们没有单源这件事
  （→ `.scratch/persistence/spec.md` 第 13 节列了五处已核实的重叠）。
