# 对象绑定不是放置问题，不进建造层

建造层（`src/GugaFramework/Construction/`）的 seam 切在放置规则上，只答「这个候选点能不能放、实际落在哪」。
它整套判据都建立在空间合法性上：世界坐标候选点、占地、格占用表或边缘间距判定。

有一类关系跟这三样都不沾：**一个对象挂在另一个对象上，不占地，也没有坐标**。
一张可堆叠的物件压在另一张上、一件道具绑在单位身上、一个槽位里放着一张卡——
逻辑上只是一条引用，画面上的位置属于表现层。

把这种关系塞进建造层要做四件事：给不存在的坐标候选点开入参、给「不占地」开一档规则、
把引用塞进不透明载荷（模块存而不读、不进快照、不进事件）、以及让每一个建造调用方都要先理解
「这一档规则是什么」。代价大于收益，且会把 seam 从「放置合法性」撑成「对象之间的任意关系」。

**决定**：绑定关系不进建造层。建造层只管空间放置，引用关系由宿主自己持有。

## Considered Options

- **扩建造层，开一档「不占地、挂在别人身上」的规则**：seam 从「空间合法性」扩成「对象关系」，
  每个适配器都要理解新规则，模块复杂度上升换不到模块级的复用——引用关系只有一个宿主用。
- **建造层存引用，宿主自己判含义**：载荷那条路模块不读也不报，宿主拿到的是不透明黑盒。
  要读就得改模块，等于回到第一条；不改则这份状态既不进快照也不进事件，重放断言看不见它。
- **宿主侧另立关系模块，建造层不管**：seam 不翻，两个放置规则仍是建造层的全部。
  关系模块自己暴露状态与事件出口，谁用谁负责。

## Consequences

- 建造层的 seam 不翻。两个放置规则就是全部，将来加第三档几何也得先证明它是放置问题。
- 引用关系不进建造层的快照段与事件出口。宿主得自己印一段，否则重放断言看不见这份状态
  （同一条已知的现状：实体层的快照段也只印 id/序号/kind，对象的自有字段由宿主自己写）。
- 收编判据不变：产物进不进最终包。宿主自立的这份模块，只有第二个宿主真要用同一形状时才搬进
  公共层——不因为「这次用到了」就搬。
- 代价是宿主各写一份。三个互不相干的宿主若都写了同一形状，那时才是收编的信号，不是现在。
